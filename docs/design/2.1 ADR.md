# 2.1 Architecture Decision Records (ADRs)

This document records the significant architectural decisions made during the design and build of AureliusPress. Each ADR captures what was decided, why, and the trade-offs accepted.

---

## ADR-001 · Ruby on Rails as the Core Framework

**Status:** Accepted

**Decision:** Use Ruby on Rails (7.2.x) as the application framework.

**Rationale:** Rails provides a mature, opinionated MVC structure that suits a content-heavy publishing platform. Convention-over-configuration accelerates development, and the ecosystem (Devise, Pundit, ActionText, ActiveStorage, Hotwire) eliminates the need for custom solutions to solved problems.

**Trade-offs:** Rails monolith limits horizontal scaling for compute-heavy tasks; accepted because the platform is read-heavy and PostgreSQL-backed caching handles load adequately at current scale.

---

## ADR-002 · STI for Documents

**Status:** Accepted

**Decision:** All document types (BlogPost, AtomicBlogPost, Page, JournalEntry) share a single `aurelius_press_documents` table via Single Table Inheritance.

**Rationale:** Document types share a common set of attributes (user, slug, title, status, visibility, published_at, comments_enabled). STI avoids table proliferation and enables `DocumentPolicy` to apply uniformly across all types. Policy and scope logic is written once.

**Trade-offs:** STI introduces nullable columns for type-specific data; mitigated by moving type-specific content into ContentBlocks (polymorphic). Sparse column risk is low given the shared attribute set.

---

## ADR-003 · STI for Fragments (Comments & Notes)

**Status:** Accepted

**Decision:** Comments and Notes share a single `aurelius_press_fragments` table via STI. Comments use the `commentable` polymorphic association; Notes use `notable`.

**Rationale:** Both types are short-lived, user-authored annotations with identical lifecycle needs (status, visibility, soft delete). Sharing a table simplifies admin fragment management and enables a single `discarded` scope across both.

**Trade-offs:** The dual polymorphic associations (`commentable` / `notable`) on the same table are non-standard; documented in CLAUDE.md Known Gotchas to prevent misuse.

---

## ADR-004 · Polymorphic Associations for Cross-Cutting Concerns

**Status:** Accepted

**Decision:** Likes, Reactions, AffiliateLinks, Categorizations, and Taggings all use polymorphic associations to attach to multiple model types without FK proliferation.

**Rationale:** Engagement and taxonomy features apply to Authors, Sources, Quotes, Documents, and ContentBlocks. Polymorphic tables keep the schema flat and the feature logic centralised in one model and one policy each.

**Trade-offs:** Polymorphic joins cannot use standard FK constraints; integrity is enforced at the application layer via Rails validations and Pundit policies.

---

## ADR-005 · Pundit for Authorisation

**Status:** Accepted

**Decision:** All controller-level authorisation uses Pundit policy objects. One policy per model. Roles are checked via helpers on the User model (`user.admin?`, `user.moderator?`, etc.).

**Rationale:** Pundit's explicit, auditable policy objects make it clear exactly what each role is permitted to do. The `DocumentPolicy` serves as the canonical reference implementation. Admin namespace access is handled by a blanket `authorize_admin_access` in `AureliusPress::Admin::ApplicationController`.

**Trade-offs:** Every new controller action requires a corresponding policy method — adds boilerplate but makes security holes impossible to miss during code review.

---

## ADR-006 · Hotwire (Turbo + Stimulus) over SPA Frameworks

**Status:** Accepted

**Decision:** All interactive UI is built with Turbo Streams (server-driven DOM updates) and Stimulus (progressive enhancement). No React, Vue, or other client-side frameworks.

**Rationale:** The platform is content-first. Server-rendered pages with selective Turbo Stream updates provide SPA-like responsiveness without the complexity of a separate frontend build pipeline or client-side state management. JSON API endpoints exist only for typeahead/decoupled consumers, not primary data fetching.

**Trade-offs:** Complex client-side interactions (drag-and-drop, rich animations) are harder without a full SPA. Accepted — the platform does not require these.

## ADR-007 · PicoCSS → NanoCSS Migration Strategy

**Status:** In Progress

**Decision:** The current frontend uses PicoCSS (classless/minimal) with a custom Tyrian Purple theme and SCSS partials. The target framework is NanoCSS.

**Rationale:** PicoCSS was selected for rapid prototyping due to its classless defaults. NanoCSS is the long-term target for its lower footprint and composability. Existing components will be retrofitted to NanoCSS; new custom components will be built on NanoCSS from the start.

**Constraint:** Do not deepen PicoCSS coupling in new work. CSS variable prefix `--ap-` is retained across the migration.

**Trade-offs:** Incremental migration creates a period of mixed styles. Managed by keeping PicoCSS as the base until each component is retrofitted.

---

## ADR-008 · ViewComponent for Reusable UI Components

**Status:** Accepted

**Decision:** Reusable UI elements are implemented as ViewComponent classes in `app/components/`. All components inherit from `ApplicationComponent`.

**Rationale:** ViewComponent co-locates Ruby logic with template rendering, enables unit testing of components in isolation, and avoids the proliferation of shared partials with implicit dependencies.

**Trade-offs:** Components are not namespaced under `aurelius_press/` (unlike models and controllers) — this is an intentional simplification since components have no model/DB coupling. `ApplicationComponent` provides the `html_attributes`, `merge_classes`, and `merge_hashes` helpers shared across all components.

---

## ADR-009 · Devise for Authentication

**Status:** Accepted

**Decision:** User authentication (sessions, registrations, password resets) is handled by Devise, mounted under `aurelius-press/users`.

**Rationale:** Devise is the Rails ecosystem standard for authentication. It handles session management, password hashing, and email-based flows without custom implementation.

**Trade-offs:** Devise's magic can obscure the auth flow for developers unfamiliar with it; mitigated by keeping Devise configuration minimal and relying on Pundit for all authorisation logic.

---

## ADR-010 · Discard (Soft Delete) Only for Fragments

**Status:** Accepted

**Decision:** Only `AureliusPress::Fragment::Fragment` (and its STI subtypes) use the `discard` gem for soft deletion. All other models hard-delete via `dependent: :destroy`.

**Rationale:** Comments and Notes benefit from soft deletion so admins can review and restore removed content. Other models (Documents, Catalogue items, Users) are managed by admins who can permanently delete. Adding soft delete broadly increases complexity without proportionate value.

**Trade-offs:** Hard-delete on documents is irreversible. Accepted — admin workflows are deliberate and backed by access controls.

---

## ADR-011 · Site Settings as a Key-Value Store

**Status:** Accepted (Happy Accident)

**Decision:** Admin-configurable settings are persisted in `aurelius_press_site_settings` as a typed key-value table (key, value, value_type, description).

**Rationale:** Publishing platforms universally require runtime-configurable settings (site name, maintenance mode, feature flags, etc.). Although this table was added autonomously by an agent that read commented-out routes, it was retained because it anticipates a genuine need. The key-value pattern is flexible and avoids schema migrations for new settings.

**Trade-offs:** Type coercion is handled in the application layer, not the database. Accepted — the `value_type` column makes the intended type explicit.
